# Контекст подготовки миров и сценариев (#2)

Дата: 2026-11-10. Исследование исходников и документации; игровые и нагрузочные проверки в рамках этой заметки не выполнялись.

## Источники и область задачи

[Issue #2](https://github.com/CheckSelfy/Bake-Mechanisms/issues/2) требует подготовить миры и воспроизводимые сценарии для блочной автофермы без входа с отдельным выходным контейнером, фермы с сущностями и набора ферм для performance-review. Сценарии должны покрывать разметку, профилирование, стазис, эмуляцию, восстановление, переполнение, штатный перезапуск и повторный цикл; для каждого нужны начальные условия и ожидаемый результат. Содержание issue получено основным агентом через GitHub.

Локальная спецификация — [spec.md](spec.md), термины — [GLOSSARY.md](../../GLOSSARY.md), архитектурное решение — [ADR-0001](../../docs/adr/0001-replace-farms-with-snapshots-and-fillers.md). Локальные материалы задачи следует хранить в `.scratch/<feature>/`, а отдельные tickets — в `issues/NN-slug.md`: [issue-tracker.md](../../docs/agents/issue-tracker.md).

## Что уже реализовано

- Плагин подключает только модуль разметки; при включении создаётся новый реестр в памяти, при выключении сохранения нет: [BakeMechanismsPlugin.java](../../src/main/java/io/github/checkselfy/bakemechanisms/BakeMechanismsPlugin.java).
- Реестр поддерживает единственное состояние `NEEDS_PROFILING`, UUID создателя, ограничения объёма, общих чанков механизмов, уникальности и расположения выходного контейнера: [FarmRegistry.java](../../src/main/java/io/github/checkselfy/bakemechanisms/marking/FarmRegistry.java).
- Реальные команды: `/bake wand|output|register|list|info <UUID>|clear`; управляющие операции доступны создателю. Профилирования, стазиса и восстановления в обработчике нет: [MarkingController.java](../../src/main/java/io/github/checkselfy/bakemechanisms/marking/MarkingController.java).
- Поддерживаются обычный/двойной сундук и бочка; двойной сундук учитывается обеими половинами: [PaperOutputResolver.java](../../src/main/java/io/github/checkselfy/bakemechanisms/marking/PaperOutputResolver.java).
- Сборка закрепляет Paper API `26.3.build.246-stable`, Java 25, JUnit/Mockito; `deploy` копирует JAR, `runServer` запускает локальный Paper: [build.gradle.kts](../../build.gradle.kts). Bash-скрипт скачивает закреплённые Paper/Mojang JAR с проверкой SHA-256, создаёт локальную конфигурацию сервера: [setup-test-server.sh](../../scripts/setup-test-server.sh).
- Ticket #3 содержит предыдущий успешный build, загрузку на Paper и общее подтверждение игроком. Покрытие каждого пункта ручного сценария отдельно не фиксировалось; это историческая запись, а не проверка текущей сессии: [03-farm-marking.md](issues/03-farm-marking.md).

## Требования будущего MVP, не текущие возможности

Полный цикл `NEEDS_PROFILING → PROFILING → READY → STASIS → NEEDS_PROFILING`, профиль за 3600 тиков, дробные накопители, bedrock-заполнитель, снимки блоков/внутренних контейнеров/сущностей, ограниченный буфер и сохранение после штатного рестарта описаны в [spec.md, §§6–13](spec.md). Исходный модуль разметки их не реализует; успешную проверку полного цикла сейчас заявлять нельзя.

Публичный API, сохранение снимка до изменения мира, явное восстановление создателем и отсутствие автоматического восстановления при загрузке чанка — действующие архитектурные ограничения, а не открытые варианты реализации: [ADR-0001](../../docs/adr/0001-replace-farms-with-snapshots-and-fillers.md).

## Что можно сделать автономно

1. Подготовить текстовые сценарии, манифесты с координатами/границами/выходными контейнерами, команды построения или воспроизводимый генератор fixture-миров; явно отделить «создано» от «запущено на Paper» и «проверено игроком».
2. Использовать отдельные чанки для механизмов разных ферм и внешние выходные контейнеры; ограничения уже заданы в [spec.md, §§4–7](spec.md) и [FarmRegistry.java](../../src/main/java/io/github/checkselfy/bakemechanisms/marking/FarmRegistry.java).
3. Описать начальные количества предметов, измеренное число серверных тиков и ожидаемые целые выдачи с дробным остатком; не сравнивать объём продукции только по настенным секундам: [spec.md, §§5.4, 8, 10, 15](spec.md).
4. Подготовить матрицу расширения performance-набора и таблицу результатов spark с одинаковыми условиями оригиналов/стазиса. «100 ферм и снижение медианного MSPT на 50%» — пример, не обязательный критерий: [spec.md, §15](spec.md).

## Открытые решения и человеческая проверка

- Конкретные дополнительные типы ферм и нагрузочный мир спецификацией не выбраны. Генератор булыжника — текстовый пример сценария, а отдельный поставляемый мир не обязателен по самой спецификации; issue #2 отдельно просит подготовить миры. Следует выбрать и зафиксировать воспроизводимую конструкцию, не утверждая, что пример сам по себе задаёт эталон: [spec.md, §15](spec.md), [issue #2](https://github.com/CheckSelfy/Bake-Mechanisms/issues/2).
- Список проверенных сериализаторов ещё не определён реализованным кодом. Любая выбранная ферма с сущностями — кандидат для будущей проверки поддержки, а не уже поддерживаемая ферма. Для восстановления нужны сравнения блоков, состояний, внутренних инвентарей, сущностей и связей транспорт/пассажиры: [spec.md, §§4, 5.2, 7, 9, 15](spec.md).
- Произвольная постройка с сущностью не доказывает отсутствие входных ресурсов или работоспособность автофермы. Перед нагрузочными выводами нужно наблюдать устойчивое производство в закреплённой версии Paper, затем проверить полный цикл с игровым клиентом: [spec.md, §§4, 8, 15](spec.md).
- Реальные MSPT и сохранность после восстановления/рестарта требуют запуска полной реализации на Paper. Создание fixture-файлов, структурные проверки и Mockito-тесты не заменяют эти результаты: [03-farm-marking.md](issues/03-farm-marking.md), [spec.md, §15](spec.md).

Отсутствие будущих модулей не мешает подготовить артефакты #2. Оно ограничивает возможную приёмку: сейчас можно проверить подготовку и разметку, а результаты полного MVP и performance-review необходимо оставить явно невыполненными до появления реализации и реального запуска.

Дополнение по текущему GitHub, полученное основным агентом через API: [#3](https://github.com/CheckSelfy/Bake-Mechanisms/issues/3) закрыта, [#4](https://github.com/CheckSelfy/Bake-Mechanisms/issues/4)–[#10](https://github.com/CheckSelfy/Bake-Mechanisms/issues/10) открыты; отдельная [correctness-review #11](https://github.com/CheckSelfy/Bake-Mechanisms/issues/11) зависит от #2/#10, [performance-review #12](https://github.com/CheckSelfy/Bake-Mechanisms/issues/12) — от #11. Следовательно, полная успешная проверка MVP не является условием завершения подготовительной #2.

Для начала подготовки обязательных решений пользователя не обнаружено. Предварительные кандидаты: автоматически собираемый кактус/сахарный тростник для блочного сценария и куры с пассивной кладкой яиц для сценария сущностей; работоспособность построек и поддержка сущностей подлежат проверке, последняя зависит от [#7](https://github.com/CheckSelfy/Bake-Mechanisms/issues/7). Простой генератор булыжника без автоматической добычи ещё не является автофермой; расходуемый TNT противоречит требованию отсутствия входных ресурсов. Эти примеры — рекомендации исследования, а не утверждение о проверенных конструкциях.
