# Bake-Mechanisms

Серверный плагин для Paper 26.3, который снижает нагрузку от автоферм без входных ресурсов: профилирует производство предметов, заменяет исходный механизм заполнителем и эмулирует его выход.

## Сборка

Требуется установленная Java для запуска Gradle wrapper (macOS, Linux или Windows). Нужная JDK 25 загружается автоматически при первой сборке.

```bash
./gradlew build
```

Готовый плагин находится в `build/libs/bake-mechanisms.jar`. Paper API используется только при компиляции, поэтому дополнительных runtime-зависимостей у плагина нет.

GitHub Actions (`.github/workflows/ci.yml`) выполняет `./gradlew build` на Java 25 для каждого pull request и push в `main`; упавший тест делает проверку красной. JAR успешного запуска скачивается со страницы запуска в разделе **Artifacts** → `bake-mechanisms` (GitHub отдаёт его zip-архивом).

## Релизы

Версия локальной сборки задаётся в `gradle.properties` (`version=…`). Чтобы выпустить релиз, запушьте тег `v<major>.<minor>.<patch>` на проверенный коммит:

```bash
git tag v0.2.0
git push origin v0.2.0
```

`.github/workflows/release.yml` собирает плагин с версией из тега без `v` (`-Pversion=0.2.0`), прогоняет все тесты, проверяет `version` в `plugin.yml` внутри JAR и только после этого создаёт GitHub Release с `bake-mechanisms.jar` и автоматическим описанием изменений. Тег с суффиксом (`v0.2.0-rc1`) публикуется как pre-release; тег другого вида отклоняется. При любой ошибке релиз не создаётся — исправьте причину, удалите тег (`git push --delete origin v0.2.0`) и поставьте его заново.

Установка на Paper-сервер остаётся ручной: скачайте `bake-mechanisms.jar` со страницы **Releases**, положите в `plugins/` и перезапустите сервер.

## Локальный сервер Paper 26.3

Первоначальная настройка скачивает закреплённую стабильную сборку Paper 26.3 build 246 и нужный ей оригинальный сервер Mojang, проверяет их SHA-256 и принимает Minecraft EULA для локального сервера:

```bash
./scripts/setup-test-server.sh
./scripts/run-test-server.sh
```

На Windows (и на любой ОС без Bash) те же шаги выполняются задачами Gradle:

```powershell
.\gradlew.bat setupServer   # только подготовка сервера
.\gradlew.bat runServer     # подготовка (если нужна), сборка, развёртывание и запуск
```

`setupServer` скачивает отсутствующие файлы, проверяет SHA-256 уже скачанных и не перезаписывает существующие `eula.txt` и `server.properties`. `runServer` вызывает её автоматически. Сервер читает команды из консоли, поэтому запускайте его в интерактивном терминале и останавливайте командой `stop`.

Скрипт запуска собирает и развёртывает плагин через `./gradlew runServer`, после чего запускает сервер на JDK 25. Файлы сервера создаются в игнорируемом Git каталоге `server/`. Локальный сервер по умолчанию работает с `online-mode=false`. Для остановки сервера введите `stop` в его консоли.

Чтобы развернуть новую сборку, остановите сервер и снова выполните `./scripts/run-test-server.sh`. Если нужно только обновить JAR в `server/plugins/` без запуска сервера, используйте `./gradlew deploy`.

Paper 26.3 поставляется со встроенным spark, поэтому отдельно устанавливать плагин не нужно. После запуска используйте `spark tps` или `spark tickmonitor` в консоли сервера для наблюдения за MSPT.

## Разметка фермы

Команды доступны любому игроку; WorldEdit не нужен.

1. Получите выделитель: `/bake wand` (нужно свободное место в инвентаре).
2. Держа его в основной руке, выберите первый угол ЛКМ, второй — ПКМ. Границы включают выбранные блоки; порядок углов не важен.
3. Выберите внешний выходной контейнер через Shift+ПКМ выделителем. Альтернатива: посмотрите на контейнер в пределах 6 блоков и выполните `/bake output`.
4. Выполните `/bake register`. В ответе будут UUID фермы и состояние `NEEDS_PROFILING`.
5. Используйте `/bake list` и `/bake info <UUID>` для просмотра своих ферм. `/bake clear` сбрасывает незавершённое выделение. Алиас команды — `/bm`.

Выходом может быть обычный сундук, двойной сундук или бочка в том же мире, вне кубоида. Двойной сундук — один выход, обе половины должны находиться снаружи. Выход нельзя использовать повторно или включить в механизм другой фермы. Механизмы разных ферм не могут занимать общие чанки, даже на разной высоте.

Предел объёма задаётся параметром `max-mechanism-volume` в `plugins/BakeMechanisms/config.yml`, по умолчанию `262144` (`64×64×64`). Изменение применяется при перезапуске. Незавершённое выделение сбрасывается при выходе игрока или смене мира.

Обычные регистрации пока хранятся в памяти до остановки сервера; общая персистентность реализуется в #8. Для ферм в стазисе сохраняется отдельный снимок с данными восстановления. Разметка сама по себе не доказывает отсутствие входных ресурсов и поддержку снимка фермы.

## Профилирование

`/bake profile <UUID>` запускает профилирование фермы из `NEEDS_PROFILING`, `/bake cancel <UUID>` отменяет его. Обе команды доступны только создателю.

- Профилирование длится ровно 3600 серверных тиков. Чанки механизма и выходного контейнера принудительно загружены тикетами плагина (с учётом общих чанков у одновременно профилируемых ферм).
- Запуск отклоняется, если внутри кубоида стоит игрок или выходной контейнер больше не совпадает с разметкой.
- Во время профилирования игроки (включая создателя и creative) не могут войти или телепортироваться в кубоид, ломать и ставить блоки, нажимать механизмы, пользоваться вёдрами и сущностями внутри, открывать или ломать выходной контейнер и ставить блоки вплотную к нему. Взрывы не разрушают выходной контейнер; взрывы внутри механизма не блокируются.
- Начальное содержимое выходного контейнера — базовый снимок, оно не считается продукцией. Выходной контейнер читается каждые `profiling.snapshot-interval` тиков (20 по умолчанию) и в конце профилирования.
- Полезный участок длится до последнего снимка перед первым полностью заполненным (каждый слот содержит полный стак). Обычные паузы до заполнения остаются в статистике.
- Профиль хранит среднюю скорость в предметах на 20 тиков по типу предмета, без зачарований и других компонентов. Опыт не учитывается. Смотрите его через `/bake info <UUID>`.
- Профиль без произведённых предметов отклоняется. Если `profiling.reject-short-useful-segment: true`, отклоняется и полезный участок короче `profiling.min-useful-ticks` (600). По умолчанию эта проверка выключена.
- Успех → `READY`, отказ, отмена, потеря выходного контейнера или остановка сервера → `NEEDS_PROFILING`. Защита и тикеты снимаются, механизм не изменяется. Создатель получает сообщение, если он в сети.
- Известные ограничения защиты: въезд в кубоид на транспорте, вход в игру или возрождение внутри кубоида, косвенные воздействия (жидкости, поршни, TNT, подожжённый снаружи). Фермы, зависящие от случайных тиков или спавна мобов, могут работать медленнее вдали от игроков: держите создателя рядом с фермой во время профилирования.

## Стазис и восстановление

После успешного профилирования (`READY`) создатель может выполнить `/bake stasis <UUID>`. Плагин сначала проверяет содержимое и сохраняет полный снимок, затем удаляет исходные сущности и заменяет весь кубоид bedrock-заполнителем. Если снимок нельзя создать или сохранить, мир не изменяется. Игрок внутри кубоида блокирует операцию.

`/bake restore <UUID>` возвращает блоки, содержимое контейнеров и поддерживаемые сущности. После восстановления состояние — `NEEDS_PROFILING`; для следующего стазиса нужен новый профиль. При ошибке восстановления снимок и защита сохраняются, область возвращается к заполнителю для повторной попытки. Загрузка чанка не восстанавливает оригинал автоматически.

- Поддерживаются обычные блоки с `BlockData`; из block entities проверены сундук (включая внутренний двойной), бочка, воронка, раздатчик, выбрасыватель, печь/плавильная печь/коптильня, крафтер, спавнер, маяк, улей и пчелиное гнездо, кафедра, стойка для варки, все цвета шалкеровых ящиков, все головы/черепа и обычные/настенные/подвесные таблички. У табличек сохраняются обе стороны текста, цвет, свечение, воск и ориентация. Сохраняются инвентари, таймеры, настройки, профили голов и пчёлы внутри ульев. Другие непроверенные block entities отклоняются.
- `STRUCTURE_VOID` сохраняется отдельно от native structure, которая обычно пропускает такие блоки. Восстанавливаются как отдельные клетки в обычной конструкции, так и кубоид только из этих блоков.
- Если поршень движется, `/bake stasis` ждёт до 10 серверных тиков (около 0,5 секунды при TPS 20) и повторяет проверку. Снимок создаётся после завершения хода. Если механизм не стабилизировался, команда просит остановить поршни; мир и профиль не изменяются. Сама промежуточная стадия `MOVING_PISTON` не копируется: публичный Structure API не восстанавливает её надёжно.
- Внутренний двойной сундук должен целиком находиться внутри кубоида. Контейнеры с ещё не сгенерированной добычей нужно сначала открыть, открытые внутренние инвентари — закрыть.
- Проверенные сущности: корова, зомби, житель, железный голем, пчела, стойка для брони, обычная вагонетка, вагонетка с сундуком, вагонетка с воронкой и предмет в мире. Другие типы отклоняются до изменения мира. Поводки необходимо снять.
- Сущности выбираются по пересечению габаритов, даже если их центр снаружи. Транспорт и все пассажиры сохраняются целиком один раз, с UUID, расположением и данными. Группа с игроком или неподдерживаемым пассажиром отклоняется.
- Заполнитель и физические блоки выходного контейнера защищены от ломания (включая creative), взрывов, поршней и обычных событий изменения блоков. Выход остаётся доступен для извлечения и добавления предметов.
- Снимки хранятся в `plugins/BakeMechanisms/farms/<UUID>/`: `snapshot.bin` и `stasis.yml`. Они восстанавливаются только на Paper 26.3; **перед обновлением сервера восстановите все фермы**. Снимок больше 128 MiB отклоняется до изменения мира.

Состояние `STASIS` и профиль сохраняются в `farm.yml` вместе с остальными фермами (#8); активный снимок (`stasis.yml`) считается главным источником. Если после сбоя ферма записана как `STASIS`, но активного снимка нет (восстановление успело завершиться), при загрузке она переводится в `NEEDS_PROFILING`.

## Эмуляция в стазисе

Пока ферма в `STASIS`, вместо исходного механизма предметы производит эмуляция по профилю фермы. Оригинал и эмуляция никогда не работают одновременно.

- Производство идёт в серверных тиках по средней скорости профиля, без адаптации к фактическому TPS. Дробные накопители точно (десятичной арифметикой, без округления скорости и случайных бросков) копят доли предметов: скорость `0,1 / 20 тиков` даёт один предмет через 200 тиков.
- Каждые `emulation.update-interval` тиков (20 по умолчанию, настраивается отдельно от `profiling.snapshot-interval`) целые предметы переносятся в выходной контейнер как новые стаки того же типа — без зачарований, повреждений, названий и других компонентов.
- Предметы, которым не хватило места, остаются в буфере выработки; пока буфер не пуст, производство приостановлено, поэтому буфер не превышает выработки одного обновления. Ничего не выбрасывается в мир. Когда игрок или воронка освобождает место, буфер переносится и производство возобновляется.
- Чанк выходного контейнера принудительно загружен на всё время стазиса (тикеты общие с профилированием); тикеты чанков механизма сняты ещё по окончании профилирования.
- Если выходной контейнер недоступен, выработка не теряется: буфер ждёт, производство приостановлено, создатель получает одно сообщение. Перенос повторяется на каждом обновлении.
- Дробные накопители и буфер записываются в `emulation.dat` после каждого изменения и при остановке сервера. После штатного рестарта эмуляция продолжается с сохранённого состояния без потерь и повторного начисления.
- `/bake restore` сначала приостанавливает производство. Если восстановление не удалось, заполнитель, снимок и буфер сохраняются, производство продолжается. После успешного восстановления новое производство прекращается, дробные доли отбрасываются, а остаток буфера сохраняется в `drain.dat` и переносится в выход по мере появления места — в том числе после рестарта.
- Пока остаток буфера переносится, новое профилирование фермы недоступно: эти предметы исказили бы профиль. Освободите место в выходном контейнере.

## Повторный цикл и удаление регистрации

- После `/bake restore` ферма в `NEEDS_PROFILING`, прежний профиль удалён. Механизм можно изменить и снова пройти `/bake profile` → `READY` → `/bake stasis` с новым профилем.
- Изменение механизма игроком в `READY` делает профиль недействительным и переводит ферму в `NEEDS_PROFILING`: ломание и установка блоков, вёдра и использование интерактивных блоков (рычаги, повторители, компараторы, двери, контейнеры и т. п.) внутри кубоида. Собственная работа фермы (редстоун, поршни, рост) профиль не сбрасывает. Игрок и создатель (если он в сети) получают сообщение.
- `/bake delete <UUID>` показывает ферму и просит подтверждения; `/bake delete <UUID> confirm` в течение 30 секунд удаляет регистрацию, профиль и каталог `farms/<UUID>/` (включая неактивный `snapshot.bin`) и снимает тикет чанка выходного контейнера. Механизм в мире не изменяется, а его чанки и выходной контейнер снова свободны для разметки. Неперенесённый остаток буфера выработки (`drain.dat`) теряется.
- Удаление доступно только создателю и только в `NEEDS_PROFILING` или `READY`, когда оригинальный механизм стоит в мире. В `STASIS` сначала выполните `/bake restore`, в `PROFILING` — `/bake cancel`. Каталог с активным снимком (`stasis.yml`) не удаляется ни при каких условиях.

## Тесты

```bash
./gradlew test
```

На Windows используйте `gradlew.bat build` / `gradlew.bat test`. Для запуска wrapper нужна установленная Java; JDK 25 для компиляции и тестов Gradle загружает автоматически. Скрипты подготовки сервера написаны для Bash; на Windows используйте `gradlew.bat setupServer` и `gradlew.bat runServer`.

Тесты проверяют геометрию, конфликты, права создателя, обработчик выделителя и разрешение контейнеров через Paper API, расчёт профиля, жизненный цикл профилирования с тикетами, защиту области и чтение выхода, эмуляцию с дробными накопителями и буфером, эмуляцию в стазисе с сохранением состояния и переносом остатка буфера, и вставку предметов в выходной контейнер. Сценарий ручной проверки на сервере описан в [задаче #3](.scratch/bake-mechanisms-mvp/issues/03-farm-marking.md).

Проверить снимки блоков, предметов и сущностей на реальном Paper без подключения клиента:

```bash
./gradlew stasisSmoke
```

На Windows — `gradlew.bat stasisSmoke`. Задача создаёт отдельный сервер в `run/stasis-smoke`, выполняет проверки и штатно останавливает его. Мир из `server/` не меняется. Тестовый плагин не входит в основной JAR. Подробности и границы интеграции с #6/#8 описаны в [stasis-integration.md](docs/development/stasis-integration.md).
