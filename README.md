# Bake-Mechanisms

Серверный плагин для Paper 26.3, который снижает нагрузку от автоферм без входных ресурсов: профилирует производство предметов, заменяет исходный механизм заполнителем и эмулирует его выход.

## Сборка

Требуется установленная Java для запуска Gradle wrapper (macOS, Linux или Windows). Нужная JDK 25 загружается автоматически при первой сборке.

```bash
./gradlew build
```

Готовый плагин находится в `build/libs/bake-mechanisms.jar`. Paper API используется только при компиляции, поэтому дополнительных runtime-зависимостей у плагина нет.

GitHub Actions (`.github/workflows/ci.yml`) выполняет `./gradlew build` на Java 25 для каждого pull request и push в `main`; упавший тест делает проверку красной. JAR успешного запуска скачивается со страницы запуска в разделе **Artifacts** → `bake-mechanisms` (GitHub отдаёт его zip-архивом).

## Релизы

Версия локальной сборки задаётся в `gradle.properties` (`version=…`). Чтобы выпустить релиз, запушьте тег `v<major>.<minor>.<patch>` на проверенный коммит:

```bash
git tag v0.2.0
git push origin v0.2.0
```

`.github/workflows/release.yml` собирает плагин с версией из тега без `v` (`-Pversion=0.2.0`), прогоняет все тесты, проверяет `version` в `plugin.yml` внутри JAR и только после этого создаёт GitHub Release с `bake-mechanisms.jar` и автоматическим описанием изменений. Тег с суффиксом (`v0.2.0-rc1`) публикуется как pre-release; тег другого вида отклоняется. При любой ошибке релиз не создаётся — исправьте причину, удалите тег (`git push --delete origin v0.2.0`) и поставьте его заново.

Установка на Paper-сервер остаётся ручной: скачайте `bake-mechanisms.jar` со страницы **Releases**, положите в `plugins/` и перезапустите сервер.

## Локальный сервер Paper 26.3

Первоначальная настройка скачивает закреплённую стабильную сборку Paper 26.3 build 246 и нужный ей оригинальный сервер Mojang, проверяет их SHA-256 и принимает Minecraft EULA для локального сервера:

```bash
./scripts/setup-test-server.sh
./scripts/run-test-server.sh
```

На Windows (и на любой ОС без Bash) те же шаги выполняются задачами Gradle:

```powershell
.\gradlew.bat setupServer   # только подготовка сервера
.\gradlew.bat runServer     # подготовка (если нужна), сборка, развёртывание и запуск
```

`setupServer` скачивает отсутствующие файлы, проверяет SHA-256 уже скачанных и не перезаписывает существующие `eula.txt` и `server.properties`. `runServer` вызывает её автоматически. Сервер читает команды из консоли, поэтому запускайте его в интерактивном терминале и останавливайте командой `stop`.

Скрипт запуска собирает и развёртывает плагин через `./gradlew runServer`, после чего запускает сервер на JDK 25. Файлы сервера создаются в игнорируемом Git каталоге `server/`. Локальный сервер по умолчанию работает с `online-mode=false`. Для остановки сервера введите `stop` в его консоли.

**Тестовый мир.** `runServer` разворачивает вместе с плагином построитель тестового мира (`bake-farm-lab.jar`) из [`test-worlds/ppl9`](test-worlds/ppl9/README.md) и [`test-worlds/ppl9-mobs`](test-worlds/ppl9-mobs/README.md). При первом запуске он создаёт рядом с основным миром отдельный мир `farm_lab` с четырьмя фермами (кактус и тростник, каждая с контрольной копией) и двумя мобофермами (скелеты и зомби). Игрок, вошедший в любой другой мир, переносится в центр `farm_lab`. Последующие запуски используют уже построенный мир и сохраняют изменения в нём. Чтобы построить мир заново (например, если ферма в нём сломана), остановите сервер и выполните `./gradlew resetFarmLab`: задача удаляет мир `farm_lab`, данные построителя, регистрации ферм Bake Mechanisms в этом мире (после перестройки они недействительны) и сохранённые позиции выхода игроков. Пока сервер запущен, задача отказывается что-либо удалять. Подсказки по лаборатории — `/farmlab list`, подробности — [ручная проверка](docs/testing/manual-farm-lab.md). Построитель предназначен только для локального сервера.

Чтобы развернуть новую сборку, остановите сервер и снова выполните `./scripts/run-test-server.sh`. Если нужно только обновить JAR в `server/plugins/` без запуска сервера, используйте `./gradlew deploy`.

Paper 26.3 поставляется со встроенным spark, поэтому отдельно устанавливать плагин не нужно. После запуска используйте `spark tps` или `spark tickmonitor` в консоли сервера для наблюдения за MSPT.

## Разметка фермы

Команды доступны любому игроку; WorldEdit не нужен.

1. Получите выделитель: `/bake wand` (нужно свободное место в инвентаре).
2. Держа его в основной руке, нажмите ЛКМ по первому углу, затем ЛКМ по второму. Границы включают выбранные блоки; порядок углов не важен. После каждого выбора выделитель сам переходит к следующему шагу, а строка над панелью предметов показывает режим, выбранные координаты и чего не хватает.
3. ЛКМ по одному или нескольким внешним выходным контейнерам. Повторный выбор того же контейнера убирает его из выделения. Альтернатива: посмотрите на контейнер в пределах 6 блоков и выполните `/bake select-output`.
   ПКМ выделителем открывает меню разметки: в нём можно выбрать, что отметит следующий ЛКМ (первый угол, второй угол, выходной контейнер), зарегистрировать ферму, очистить выделение и посмотреть подсказку. Подробно — [docs/commands.md](docs/commands.md#bake-wand).
4. Нажмите в меню «Зарегистрировать ферму» или выполните `/bake register [имя]`. В ответе будут имя, UUID фермы и состояние `NEEDS_PROFILING`.
5. `/bake manage` (или «Мои фермы» в меню выделителя) открывает экран ферм: состояние каждой фермы показано блоком, а профилирование, стазис, выход из стазиса и удаление выполняются кнопками. В чате фермы показывают `/bake list` и `/bake info <ферма>`. `/bake unselect` сбрасывает незавершённое выделение. Алиас команды — `/bm`.

Здесь и далее `<ферма>` — имя фермы или `--id <UUID>`. Имя необязательно и автоматически не создаётся: ферма без имени доступна только через `--id`. Имя задаётся при регистрации или командой `/bake rename <ферма> <имя>`, состоит из 1–32 латинских букв, цифр, `_` и `-`, различает регистр (`Iron` и `iron` — разные имена) и уникально среди ферм одного создателя.

Выходным контейнером может быть обычный сундук, двойной сундук или бочка в том же мире, вне кубоида. Двойной сундук — один выходной контейнер, обе половины должны находиться снаружи. У фермы может быть до `max-output-containers` выходных контейнеров (по умолчанию 8); их порядок и состав фиксируются при регистрации — чтобы изменить выходные контейнеры, удалите и заново зарегистрируйте ферму. Выходной контейнер нельзя использовать повторно или включить в механизм другой фермы. Механизмы разных ферм не могут занимать общие чанки, даже на разной высоте.

Предел объёма задаётся параметром `max-mechanism-volume` в `plugins/BakeMechanisms/config.yml`, по умолчанию `262144` (`64×64×64`). Изменение применяется при перезапуске. Незавершённое выделение сбрасывается при выходе игрока или смене мира.

Регистрации сохраняются в `plugins/BakeMechanisms/farms/<UUID>/farm.yml` и загружаются при запуске. Для ферм в стазисе сохраняется также отдельный снимок с данными восстановления. Разметка сама по себе не доказывает отсутствие входных ресурсов и поддержку снимка фермы.

## Профилирование

Для ручной проверки на двух реальных фермах из карты PPL9 запустите `python scripts/farm-lab.py run` и подключитесь Minecraft Java 26.3 к `127.0.0.1:25566`. [Пошаговая инструкция](docs/testing/manual-farm-lab.md) описывает разметку цветных углов, полный цикл, рестарт и запись результатов. [Извлечённые NBT-структуры](test-worlds/ppl9/README.md) хранятся в репозитории и используются также командой `python scripts/farm-lab.py headless` на отдельной копии мира.

`/bake profile <ферма>` запускает профилирование фермы из `NEEDS_PROFILING`, `/bake cancel-profiling <ферма>` отменяет его. `/bake sprint <ферма>` ускоряет сервер ванильной `/tick sprint` ровно до конца профилирования; команда выполняется от имени игрока, поэтому нужно право ванильной `/tick` (`minecraft.command.tick`); без него команда отвечает ошибкой и скрыта из автодополнения. Ускорение действует на весь сервер. Все команды доступны только создателю.

- `/bake profile <ферма>` измеряет 3600 серверных тиков (3 минуты при 20 TPS), `/bake profile-long <ферма>` — 36000 тиков (30 минут). Конфиг менять не нужно; разные фермы могут измеряться разное время одновременно. `/bake sprint` и индикатор учитывают длительность каждого замера. Чанки механизма и выходного контейнера принудительно загружены тикетами плагина (с учётом общих чанков у одновременно профилируемых ферм).
- Каждый физический блок выхода должен находиться снаружи, в кубоиде механизма, расширенном на один блок. Для двойного сундука проверяются обе половины. Сборщики и подающие воронки включайте в исходный механизм.
- Защищается кубоид, расширенный на два блока по всем осям; его чанки тоже удерживаются загруженными. Перед запуском игроки должны выйти из этой области. Её пересечение с чужими механизмами/выходами или другой активной защитой отклоняется.
- Перед замером опустошите внутренние инвентари. Исключения: внутренние воронки, ножницы в раздатчике и карманы жителей. После успешных проверок запуска **все лежащие предметы внутри кубоида механизма удаляются безвозвратно**; предметы снаружи, включая защитный пояс, сохраняются. Начальный суммарный запас внутренних воронок и выходов считается базой: его перемещение не создаёт выработку. Новая продукция, оставшаяся в воронках, входит в прирост. Если один тип продукции с запасом воронок нельзя однозначно распределить между несколькими выходами, замер отклоняется с объяснением; разделите выходы по типам продукции. Внешние подающие воронки/выбрасыватели, пограничные двойные сундуки и неоднозначные источники отклоняются с причиной. Начальное снаряжение мобов допускается, но попадание предмета того же типа в продукцию прерывает замер: запас нельзя надёжно отличить от производства.
- Во время профилирования игроки (включая создателя и creative) не могут входить или телепортироваться в защитную область, менять блоки, пользоваться механизмами, вёдрами, сущностями и контейнерами. Внешние жидкости и поршни не могут менять область; выход защищён от взрывов. Внутренняя работа фермы сохраняется.
- Подавать предметы в механизм и выходы можно только из инвентарей внутри механизма. Выход можно разгружать наружу, но возвращать предметы обратно нельзя. Старые, внешние и брошенные игроками предметы не подбираются сборщиками; их смешивание с новой продукцией блокируется. Требуется действующее `hopper.disable-move-event: false` в Paper.
- Начальное содержимое выходных контейнеров — базовый снимок, оно не считается продукцией. Все выходные контейнеры читаются каждые `profiling.snapshot-interval` тиков (20 по умолчанию) и в конце профилирования.
- Скорость измеряется отдельно для каждого выходного контейнера. Полезный участок общий: он начинается со снимка, в котором суммарный запас воронок и выходов впервые вырос относительно старта, и длится до последнего снимка перед заполнением любого выхода (каждый слот содержит полный стак). Простой перенос начального запаса участок не запускает. Обычные паузы до заполнения остаются в статистике. Разгрузка за пределы измеряемых инвентарей разрешена, но уменьшает измеряемый прирост; для точного замера оставьте выходы с достаточным свободным местом.
- Профиль хранит среднюю скорость каждого выходного контейнера в предметах на 20 тиков по типу предмета, без зачарований и других компонентов. Опыт не учитывается. Выходной контейнер, в который ничего не поступило, допустим. Смотрите профиль через `/bake info <ферма>` или на экране `/bake manage`; там скорость показана в предметах за тик (сохранённая скорость, делённая на 20).
- Профиль без произведённых предметов отклоняется. Если `profiling.reject-short-useful-segment: true`, отклоняется и полезный участок короче `profiling.min-useful-ticks` (600). По умолчанию эта проверка выключена.
- Успех → `READY`, отказ, отмена, потеря выходного контейнера или остановка сервера → `NEEDS_PROFILING`. Защита и тикеты снимаются, механизм не изменяется. Создатель получает сообщение, если он в сети.
- Защита рассчитана на обычных игроков и ванильный транспорт предметов; административные команды и прямые изменения мира другими плагинами не изолируются. Вход в игру/возрождение внутри области и перевозка игроков сохраняют ограничения прежней защиты. Фермы со случайными тиками или спавном мобов могут работать медленнее вдали от игроков: держитесь рядом, снаружи защитной области. [Проверка защиты входов #25](docs/testing/profiling-input.md).

## Стазис и восстановление

После успешного профилирования (`READY`) создатель может выполнить `/bake stasis <ферма>`. Плагин сначала проверяет содержимое и сохраняет полный снимок, затем удаляет исходные сущности и заменяет весь кубоид декоративным зелёным слаймом. Полупрозрачная оболочка, плотная сердцевина и пиксельное лицо подстраиваются под размер региона; каждый блок кубоида заполнен, блоки снаружи не добавляются. Если снимок нельзя создать или сохранить, мир не изменяется. Игрок внутри кубоида блокирует операцию.

Оформление задаёт `stasis.filler` в конфиге: палитра, рисунок `BANDS`/`PANELS`, размер узора и направление лица. `AUTO` выбирает сторону с наибольшим числом выходных контейнеров; двойной сундук даёт один голос. При равенстве голосов предпочтение получает более широкая грань среди победителей, далее используется постоянный порядок сторон. Наружные материалы — стекло; отскока, липкости, блоков с тиками, сущностей и анимации нет. Выбранные палитра, направление и версия рисунка сохраняются в `stasis.yml` и используются при откате после ошибки. Смена конфига влияет только на новые входы в стазис. Старые бедроковые заполнители остаются на месте и восстанавливаются прежним снимком. [Галерея размеров и проверка #32](docs/testing/slime-filler.md).

`/bake unstasis <ферма>` возвращает блоки, содержимое контейнеров и поддерживаемые сущности. После восстановления состояние — `NEEDS_PROFILING`; для следующего стазиса нужен новый профиль. При ошибке восстановления снимок и защита сохраняются, область возвращается к заполнителю для повторной попытки. Загрузка чанка не восстанавливает оригинал автоматически.

- Поддерживаются обычные блоки с `BlockData`; из block entities проверены сундук (включая внутренний двойной), бочка, воронка, раздатчик, выбрасыватель, печь/плавильная печь/коптильня, крафтер, спавнер, маяк, улей и пчелиное гнездо, кафедра, стойка для варки, все цвета шалкеровых ящиков, все головы/черепа и обычные/настенные/подвесные таблички. У табличек сохраняются обе стороны текста, цвет, свечение, воск и ориентация. Сохраняются инвентари, таймеры, настройки, профили голов и пчёлы внутри ульев. Другие непроверенные block entities отклоняются.
- `STRUCTURE_VOID` сохраняется отдельно от native structure, которая обычно пропускает такие блоки. Восстанавливаются как отдельные клетки в обычной конструкции, так и кубоид только из этих блоков.
- Если сущность механизма умирает, удаляется, садится или высаживается (жокеи на курицах), ещё добавляется в мир или сущности чанка ещё загружаются, `/bake stasis` сам повторяет попытку до 100 тиков (5 секунд при TPS 20) с сообщениями о ходе стабилизации; ручные `/tick freeze`, `/kill` и высадка не нужны. Снимок создаётся в первый стабильный тик.
- Если поршень движется, `/bake stasis` ждёт до 10 серверных тиков (около 0,5 секунды при TPS 20) и повторяет проверку. Снимок создаётся после завершения хода. Если механизм не стабилизировался, команда просит остановить поршни; мир и профиль не изменяются. Сама промежуточная стадия `MOVING_PISTON` не копируется: публичный Structure API не восстанавливает её надёжно.
- Обычные мобы из спавнера (исчезающие вдали от игроков) поддерживаются без изменения их постоянства: после восстановления они остаются такими же. Одиночные тела погибших мобов не сохраняются (их добыча уже выпала) и удаляются вместе с оригиналами.
- Внутренний двойной сундук должен целиком находиться внутри кубоида. Контейнеры с ещё не сгенерированной добычей нужно сначала открыть, открытые внутренние инвентари — закрыть.
- Поддержан 91 создаваемый живой тип Paper 26.3 build 246, включая овец, кур, свиней, лошадей,
  приручаемых животных, рыб и мобов. Дракон Края и игроки исключены. Дополнительно поддержаны обычная
  вагонетка, вагонетка с сундуком, вагонетка с воронкой и выпавший предмет. Поводки необходимо снять;
  особые состояния с внешними связями или потерями NBT отклоняются до изменения мира.
- [Матрица NBT и границы поддержки](docs/testing/entity-nbt.md): UUID, свойства и пассажиры проверяются
  после настоящего перезапуска Paper. Состояния, которые native NBT теряет (например, нестандартное
  движение вагонетки, таймер после ужаления пчелы), отклоняются до стазиса. Активные цели мобов
  сохраняются отдельно по UUID и восстанавливаются после всех сущностей; они не блокируют стазис.
- Сущности выбираются по пересечению габаритов, даже если их центр снаружи. Транспорт и все пассажиры сохраняются целиком один раз, с UUID, расположением и данными. Группа с игроком или неподдерживаемым пассажиром отклоняется.
- Заполнитель и физические блоки выходного контейнера защищены от ломания (включая creative), взрывов, поршней и обычных событий изменения блоков. Выход остаётся доступен для извлечения и добавления предметов.
- Снимки хранятся в `plugins/BakeMechanisms/farms/<UUID>/`: `snapshot.bin` и `stasis.yml`. Они восстанавливаются только на Paper 26.3; **перед обновлением сервера восстановите все фермы**. Снимок больше 128 MiB отклоняется до изменения мира.

Состояние `STASIS` и профиль сохраняются в `farm.yml` вместе с остальными фермами (#8); активный снимок (`stasis.yml`) считается главным источником. Если после сбоя ферма записана как `STASIS`, но активного снимка нет (восстановление успело завершиться), при загрузке она переводится в `NEEDS_PROFILING`.

## Эмуляция в стазисе

Пока ферма в `STASIS`, вместо исходного механизма предметы производит эмуляция по профилю фермы. Оригинал и эмуляция никогда не работают одновременно.

- Производство идёт в серверных тиках по средней скорости профиля, без адаптации к фактическому TPS. Дробные накопители точно (десятичной арифметикой, без округления скорости и случайных бросков) копят доли предметов: скорость `0,1 / 20 тиков` даёт один предмет через 200 тиков.
- Каждые `emulation.update-interval` тиков (20 по умолчанию, настраивается отдельно от `profiling.snapshot-interval`) целые предметы переносятся в выходные контейнеры как новые стаки того же типа — без зачарований, повреждений, названий и других компонентов. Каждый выходной контейнер получает только то, что ферма производила в него при профилировании.
- Предметы, которым не хватило места, остаются в буфере выработки своего выходного контейнера. Если хотя бы в одном выходном контейнере нет места, новое производство приостанавливается для всех выходных контейнеров, а создатель получает одно сообщение. Выходные контейнеры, в которых есть место, продолжают получать свой уже произведённый буфер. Производство возобновляется (с сообщением), когда буферы всех выходных контейнеров перенесены, поэтому буфер каждого выходного контейнера не превышает выработки одного обновления. Ничего не выбрасывается в мир.
- Чанки выходных контейнеров принудительно загружены на всё время стазиса (тикеты общие с профилированием); тикеты чанков механизма сняты ещё по окончании профилирования.
- Если выходной контейнер недоступен, выработка не теряется: буфер ждёт, производство приостановлено, создатель получает одно сообщение. Перенос повторяется на каждом обновлении.
- Выработка начисляется только за игровые тики. Пока сервер заморожен ванильной `/tick freeze`, миры не тикают, поэтому стоят и эмуляция, и профилирование; `/tick step` и `/tick sprint` считаются обычными игровыми тиками. Paper продолжает вызывать задачи плагинов во время заморозки, и раньше это начисляло выработку за замороженное время (#12).
- Дробные накопители и буфер записываются в `emulation.dat` после каждого изменения и при остановке сервера. После штатного рестарта эмуляция продолжается с сохранённого состояния без потерь и повторного начисления.
- `/bake unstasis` сначала приостанавливает производство. Если восстановление не удалось, заполнитель, снимок и буфер сохраняются, производство продолжается. После успешного восстановления новое производство прекращается, дробные доли отбрасываются, а остаток буфера сохраняется в `drain.dat` и переносится в выход по мере появления места — в том числе после рестарта.
- Пока остаток буфера переносится, новое профилирование фермы недоступно: эти предметы исказили бы профиль. Освободите место в выходном контейнере.

## Повторный цикл и удаление регистрации

- После `/bake unstasis` ферма в `NEEDS_PROFILING`, прежний профиль удалён. Механизм можно изменить и снова пройти `/bake profile` → `READY` → `/bake stasis` с новым профилем.
- Изменение механизма игроком в `READY` делает профиль недействительным и переводит ферму в `NEEDS_PROFILING`: ломание и установка блоков, вёдра и использование интерактивных блоков (рычаги, повторители, компараторы, двери, контейнеры и т. п.) внутри кубоида. Собственная работа фермы (редстоун, поршни, рост) профиль не сбрасывает. Игрок и создатель (если он в сети) получают сообщение.
- `/bake unregister <ферма>` показывает ферму и просит подтверждения; `/bake unregister <ферма> confirm` в течение 30 секунд удаляет регистрацию, профиль и каталог `farms/<UUID>/` (включая неактивный `snapshot.bin`) и снимает тикет чанка выходного контейнера. Механизм в мире не изменяется, а его чанки и выходной контейнер снова свободны для разметки. Неперенесённый остаток буфера выработки (`drain.dat`) теряется.
- Удаление доступно только создателю и только в `NEEDS_PROFILING` или `READY`, когда оригинальный механизм стоит в мире. В `STASIS` сначала выполните `/bake unstasis`, в `PROFILING` — `/bake cancel-profiling`. Каталог с активным снимком (`stasis.yml`) не удаляется ни при каких условиях.

## Тесты

```bash
./gradlew test
```

На Windows используйте `gradlew.bat build` / `gradlew.bat test`. Для запуска wrapper нужна установленная Java; JDK 25 для компиляции и тестов Gradle загружает автоматически. Скрипты подготовки сервера написаны для Bash; на Windows используйте `gradlew.bat setupServer` и `gradlew.bat runServer`.

Тесты проверяют геометрию, конфликты, права создателя, обработчик выделителя и разрешение контейнеров через Paper API, расчёт профиля, жизненный цикл профилирования с тикетами, защиту области и чтение выхода, эмуляцию с дробными накопителями и буфером, эмуляцию в стазисе с сохранением состояния и переносом остатка буфера, и вставку предметов в выходной контейнер. Сценарий ручной проверки на сервере описан в [задаче #3](.scratch/bake-mechanisms-mvp/issues/03-farm-marking.md).

Проверить снимки блоков, предметов и сущностей на реальном Paper без подключения клиента:

```bash
./gradlew stasisSmoke
```

На Windows — `gradlew.bat stasisSmoke`. Задача создаёт отдельный сервер в `run/stasis-smoke`, выполняет проверки и штатно останавливает его. Мир из `server/` не меняется. Тестовый плагин не входит в основной JAR. Подробности и границы интеграции с #6/#8 описаны в [stasis-integration.md](docs/development/stasis-integration.md).
