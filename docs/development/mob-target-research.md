Research date: 2026-11-11. Paper revision: `b31b4b5`. This is source/bytecode evidence and a proposed verification matrix, not a report of passing runtime tests.

## What the public target methods actually do

`org.bukkit.craftbukkit.entity.CraftMob.setTarget` calls native `Mob.setTarget(target, null)` (including for a null target). It refuses world-generation state. `getTarget` delegates to the native virtual getter. Native `net.minecraft.world.entity.Mob.setTarget(LivingEntity, TargetReason)` writes its ordinary `target` field after `asValidTarget`; its event branch runs only when the reason is nonnull. Consequently **this public API setter does not dispatch EntityTargetLivingEntityEvent on this build**. A listener cancelling native AI target acquisition does not cancel this setter. Do not describe an immediate getter mismatch as event cancellation. A plugin may still change/remove entities during spawn callbacks or later ticks. [Primary: those two methods in `CraftMob` and the native `Mob` overload.]

`Mob.asValidTarget` hides creative/spectator players and targets rejected by virtual `canAttack`. Base `Mob.canAttack` rejects ghasts and delegates to `LivingEntity.canAttack`; the latter rejects players in peaceful and entities that cannot be seen as enemies (including invulnerable/dead/spectator state through its predicates). Species can impose additional rules. There is no same-world or online-player validation in `CraftMob.setTarget` itself. Explicitly require a resolved live, valid `LivingEntity` in the source's world, and an online player when applicable; verify the resulting getter UUID immediately. Do not force the setter to preserve a now-invalid target. [Primary: `Mob.asValidTarget`, `Mob.canAttack`, `LivingEntity.canAttack`, `canBeSeenAsEnemy`, `canBeSeenByAnyone`.]

There is a major public API limitation: native `AbstractPiglin` (piglin and brute), `Warden`, `Zoglin`, `Hoglin`, `Axolotl`, `Frog`, and `Breeze` override `getTarget()` to return `getTargetFromBrain()`. That method reads `MemoryModuleType.ATTACK_TARGET`. None of these inspected native classes or their Craft wrappers overrides `setTarget` to update that memory. Thus a public `setTarget` call can write the ordinary field while the public getter continues returning null or the previous brain target. This list is verified examples, not an exhaustive scan of all future species. [Primary: named native classes under `net.minecraft.world.entity`, their `getTarget` methods; Craft wrappers' declared signatures; `Mob.getTargetFromBrain`.]

`MemoryModuleType` registers `attack_target` without a codec, unlike persistent memories registered with codecs. The public final `MemoryKey` class has no `ATTACK_TARGET`, `NEAREST_HOSTILE`, or general entity-target key, and `getByKey` only retrieves registered public keys; it is not a way to construct a missing key. `CraftLivingEntity.setMemory` maps a public key through `CraftMemoryKey` and cannot supply the missing key through supported API. The API JAR contains no separate public brain API. Warden's public anger methods manipulate `AngerManagement`; `setDisturbanceLocation` supplies a location to AI. Neither is an exact setter for `ATTACK_TARGET`. Increasing anger and letting the brain choose a target is behavioral reacquisition, not immediate identity restoration. [Primary: `MemoryModuleType` static initializer; API `MemoryKey` signatures; `CraftLivingEntity.setMemory`; `CraftWarden.setAnger`, `increaseAnger`, `setDisturbanceLocation`.]

Therefore a claim of **exact immediate target restoration for every mob through public Paper API** is unsupported on this build. Keep this limitation explicit in acceptance criteria. Native serialization plus a UUID sidecar can solve ordinary-field targets; it cannot by itself solve the missing brain setter. Broad farm support can instead include brain mobs with documented normal AI reacquisition and real tick evidence. If exact brain targeting is mandatory, the implementation boundary must change (a supported Paper API addition or an explicitly authorized native adapter).

### Narrow pinned bridge for exact brain target restoration

The implementation decision can deliberately permit a small reflective adapter for this missing operation, while retaining opaque native serialization and ordinary public API everywhere else. This is a version-specific exception to the current class comment promising no NMS/reflection, not a public Paper capability. It has no compile-time NMS dependency and needs neither private fields nor `setAccessible`.

Resolve these **public** members once, using the server class loader and exact names from the pinned bytecode:

- `org.bukkit.craftbukkit.entity.CraftMob.getHandle()` and `CraftLivingEntity.getHandle()` for source/target native handles.
- `net.minecraft.world.entity.LivingEntity.getBrain()`.
- `net.minecraft.world.entity.ai.memory.MemoryModuleType.ATTACK_TARGET` (public static final).
- `net.minecraft.world.entity.ai.memory.MemoryStatus.REGISTERED` (public enum constant).
- `net.minecraft.world.entity.ai.Brain.checkMemory(MemoryModuleType, MemoryStatus)`.
- `Brain.setMemory(MemoryModuleType, Object)`; explicitly resolve the erased `Object` parameter because there is also an `Optional` overload.
- Optional validation: public native `Mob.canAttack(LivingEntity)`; supplement it with the creative/spectator and same-world checks described above, because `asValidTarget` is protected.

`Brain.setMemoryInternal(MemoryModuleType,Object)` silently does nothing if the brain has no slot for that module. `checkMemory(ATTACK_TARGET, REGISTERED)` verifies slot registration independently of whether a value is currently present. Check this before writing; never equate successful reflection invocation with successful restore. For an ordinary source use public `Mob.setTarget`; for a confirmed brain source use the adapter. Both paths must check the public getter UUID immediately afterward. Null restoration may call the same Object overload with null (or public `eraseMemory`); keep the relation semantics explicit. [Primary: exact signatures and bytecode in `Brain`, `MemoryStatus`, `MemoryModuleType`, `LivingEntity`, `CraftMob`, `CraftLivingEntity`.]

Probe all reflection signatures at startup and registration during preparation, before removing entities or changing blocks. A missing capability is a precise pinned-version compatibility error, not a reason to drop every farm's state. Do not use only a hardcoded species list as the capability test: registered memory plus known getter behavior and actual getter readback are stronger. Do not set attack memory on ordinary mobs merely because a slot happens to exist. Test each current brain-backed example and the full supported-type matrix on this exact artifact. Brain writes bypass normal target-acquisition events just as this build's explicit public setter does; subsequent AI ticks can still replace the target. Source-level and bytecode facts justify the adapter's shape, but real-server tests must establish runtime fidelity.

## Farm relationships are not interchangeable

| Relationship | Pinned implementation evidence | What to verify |
| --- | --- | --- |
| Zombie attacking villager | Ordinary mob attack target; can be captured by `Mob.getTarget`. | UUID restored immediately, then pursuit/continued targeting under valid AI conditions. |
| Villager afraid of zombie | `VillagerHostilesSensor` writes `NEAREST_HOSTILE`; its hostile table includes zombies within 8 blocks. `VillagerPanicTrigger` checks that memory and selects `Activity.PANIC`. | Fear/panic and iron-farm operation after sensing resumes, independently of zombie target. Setting villager attack target is not fear restoration. |
| Creeper fleeing cat/ocelot | `net.minecraft.world.entity.monster.Creeper.registerGoals` adds `AvoidEntityGoal` for cat and ocelot at priority 3, range 6, speeds 1 and 1.2. | Creeper moves away after restore with cat still present. The cat is not its attack target. |
| Slime attracted to iron golem | `net.minecraft.world.entity.monster.cubemob.Slime.addTargetingGoals` installs `NearestAttackableTargetGoal<IronGolem>` at priority 3 (player goal priority 1). | Golem UUID target and approach/hopping after restore with no competing survival players. This is attack acquisition, not the creeper's avoidance mechanism. |

Transient navigation paths, running goals and sensor phase are not serialized AI checkpoints. Native entity persistence and restored relationships should let these farm behaviors resume; avoid rejecting an otherwise supported farm merely because its mobs are currently targeting or avoiding something. The current blanket rejection in `PaperEntitySnapshots.validateRuntimeState` prevents the zombie/slime cases and should be replaced by the agreed target policy. [Local primary implementation: `src/main/java/io/github/checkselfy/bakemechanisms/stasis/PaperEntitySnapshots.java`.]

## Recommended sidecar and restore semantics

Capture a relation `(source UUID, target UUID, target world UUID)` for every observable nonnull `Mob.getTarget`, including passengers and targets outside the cuboid or players. Do not serialize external entities into the farm merely because they are targeted. Distinguish internal targets by membership in the full captured member set. Keep native bytes opaque. Version the `SnapshotPayload` envelope and validate duplicate sources, source membership, UUIDs and truncation before mutation; existing versions decode with no sidecar. [Local primary: `SnapshotPayload.EntityGroup`, `encode`, `decode`; `PaperEntitySnapshots.capture`, `prepare`, `spawn`.]

Restore in two passes on the server thread: first spawn **all** roots and passengers and build the complete UUID map; then resolve internal targets from that map and external targets through the server. This handles targets in later groups, mutual targeting and passenger relations without stale handles. Apply and verify ordinary targets before yielding a tick. Do not retain original entity Java references across removal or restart.

An internal expected target missing after successful preparation/spawn is structural restore failure, not a normal external fallback. An external target may have died, unloaded, logged out, changed world or become invalid during stasis: restore the farm, omit that unavailable relation, and let native AI reacquire; do not make the farm unrestorable because an external player left. Record/report this bounded fallback. Likewise, a formerly valid target now rejected by native rules should not be forced. Decide explicitly whether an unexpected getter mismatch for a still-valid ordinary target fails/rolls back restoration; do not silently claim fidelity. Brain targets need the separate policy above, rather than treating every setter mismatch as successful restoration.

## Real tick verification through public API

Use an isolated loaded flat arena in non-peaceful difficulty, solid floor, roof/night for zombies, no unrelated mobs or survival players, and scheduled tick counters with bounded deadlines rather than wall-clock sleeps. Set persistence/removal-at-distance settings through API; keep AI/awareness enabled during behavior observations. Disable AI only for the immediate identity test, then re-enable it. Remove only competing goals through Paper's public MobGoals API if necessary for a fixture; do not remove the behavior under test. Save independent expected UUIDs and properties outside the serialized payload.

1. Ordinary relation matrix: zombie-to-villager, slime-to-golem, mutual ordinary targets, later-group target, passenger target, live external living entity, online survival player. Immediately after restore (before yielding), assert getter UUID. Repeat after a full clean server restart. Null-target rows, dead/missing/unloaded external targets, changed-world target, creative/spectator player and spawn failure exercise fallback/failure policy. A target-event cancellation listener should observe that explicit setter restoration bypasses that event on this exact build; separately verify native AI acquisition cancellation normally.
2. Zombie/villager behavior: contain a zombie in visible proximity (less than 8 blocks) behind a barrier it cannot cross, place villagers in a supported iron-farm layout with beds/sleep history, and wait for a bounded observable panic/iron-golem result. Establish that same layout works before stasis, restore it, then require behavior again. Do not use `getTarget` on villagers as the fear assertion. Panic motion can be observed through positions; final farm output/golem spawning is stronger but requires all ordinary village conditions and a longer tick budget.
3. Creeper/cat: place a stationary cat within 6 blocks of an AI-enabled creeper on a wide navigable floor. Keep the cat stationary with its own AI disabled; avoid another attack target. Establish a bounded increase in separation before capture and after restore. Navigation/random position selection means a specific first tick/direction is not deterministic. Use a fixed arena and a generous bounded observation, then a cat-absent control; assert repeated retreat, not one arbitrary displacement. Native sidecar assertions alone cannot establish this behavior.
4. Slime/golem: use a non-tiny slime with AI enabled and a stationary golem (golem AI disabled), with no survival player competitor. First wait for native `getTarget` to equal the golem UUID, then capture and verify the same UUID immediately on restore. In a safe bounded arena, require subsequent approach/hopping toward the golem. Avoid setting the target solely to manufacture the behavior fixture; that would not test natural acquisition.
5. Brain contrast: for piglin/brute, hoglin/zoglin, warden, axolotl, frog and breeze, create valid natural prey/enemy conditions and first observe a nonnull target. Compare detached native round-trip and post-spawn getter; demonstrate `setTarget` does not restore it immediately. If accepting reacquisition, keep the relevant stimulus and test within a bounded species-specific tick budget. Warden `setAnger` can prepare anger through API, but observing later targeting must be reported separately from immediate restoration. Do not claim a public memory setter exists.

Public API alone cannot make stochastic native path selection mathematically deterministic. Deterministic test orchestration means known arena/state, explicit readiness predicates, tick-based deadlines, baseline/control cases and reproducible assertions. Distinguish immediate exact-identity tests from bounded behavioral recovery tests in results.

### No-player behavioral smoke configuration

Pinned activation bytecode supports running these tests without human players. In the test server's `spigot.yml`, set `world-settings.default.entity-activation-range` entries `animals`, `monsters`, `villagers`, `raiders`, `water`, `flying-monsters`, and `misc` to `0` **before creating or deserializing fixture entities**. `ActivationRange.initializeEntityActivationState` returns true when an entity's category range is at most zero; the native `Entity` constructor stores that return value as `defaultActivationState`, and `ActivationRange.checkIfActive` returns true for it. Merely changing settings after construction does not establish that stored state. This is a fixture/server configuration, not a recommendation to disable production activation optimization. [Primary: `io.papermc.paper.entity.activation.ActivationRange.initializeEntityActivationState`, `checkIfActive`; native `Entity` constructor.]

Add public plugin chunk tickets covering the arena and navigation margin. On this exact build, `CraftWorld.addPluginChunkTicket` delegates to `TicketStorage.addPluginRegionTicket`, which uses `PLUGIN_TICKET` at `ChunkMap.FORCED_TICKET_LEVEL`; `ChunkMap` initializes that level from `ChunkLevel.byStatus(FullChunkStatus.ENTITY_TICKING)`. Thus this is stronger than merely loading a chunk. Wait for public `Chunk.getLoadLevel()` to report `ENTITY_TICKING`, `isEntitiesLoaded()` to be true, and fixture `getTicksLived()` to advance before judging AI. Allow ticket propagation a few scheduled ticks; retain tickets until cleanup. [Primary: those methods/static initializer in the pinned server; public `Chunk` and `Chunk.LoadLevel` signatures in the pinned API.]

For a compact smoke, capture with fixture AI disabled, restore, make immediate target/property assertions, then re-enable the moving mob's AI and observe for 120 scheduled ticks on a wide vanilla solid floor. A stationary stimulus (cat, golem, fenced zombie) can keep its own AI disabled. For the creeper, public `VanillaGoal.AVOID_ENTITY` is `GoalKey<Creature>` with key `minecraft:avoid_entity`; both native cat and ocelot avoidance goals have this key. If random stroll interferes, enumerate `MobGoals.getAllGoals(creeper)` and remove each goal whose key differs, retaining **all** matching avoidance goals. Apply the same fixture pruning after restore because goal selectors are not persisted. Do not keep `CAT_AVOID_ENTITY`, which refers to a cat's own goal rather than the creeper avoiding a cat. [Primary: API `VanillaGoal` static initializer; `MobGoalHelper.getKey`; `Creeper.registerGoals`; public `MobGoals` signatures.]

Slime-to-golem natural target acquisition exists in vanilla on this build (`Slime.addTargetingGoals`, priority 3), so the smoke can wait for public target identity without a player or a custom goal. Keep slime movement AI enabled and do not disable golem invulnerability rules by making the golem invulnerable: the native targeting predicate rejects invulnerable enemies. Disable the golem's AI instead. Villager smoke can observe retreat/motion from a visible zombie behind a fence within 8 blocks before and after restore; because public `NEAREST_HOSTILE` is absent, call this behavioral evidence rather than exact fear-memory restoration. Use distance gain relative to the stationary threat and a baseline/control, rather than any movement in any direction. A 120-tick motion smoke does not establish the complete iron-golem production lifecycle.

### Valid targets for the immediate all-mob matrix

An adult live, noninvulnerable sheep is a useful ordinary target fixture, but not universal: `Breeze.canAttack` accepts only players or iron golems and then checks superclass validity. Use an iron golem for the breeze. `Warden.canAttack` delegates to `canTargetEntity`, requiring a living target in the same world, not creative/spectator or allied, not an armor stand or warden, alive/noninvulnerable, and within the world border; an ordinary sheep meets those conditions. `IronGolem.canAttack` rejects creepers and, for player-created golems, players. `TamableAnimal.canAttack` rejects its owner. These checks must be respected by the restoration helper rather than bypassed by writing a brain memory. [Primary: named native methods in pinned server bytecode.]

The inspected `Frog`, `Axolotl`, `WitherBoss`, `Hoglin`, `Zoglin`, `AbstractPiglin`, `Monster`, `Animal`, and `PathfinderMob` declare no `canAttack` override. Sheep can exercise their immediate setter/getter identity, although it is not necessarily natural prey. A size-1 slime for the frog and an appropriate aquatic prey fixture for axolotl make subsequent natural behavior more representative. Sensor acquisition predicates, attack-goal prey selection and native `canAttack` are distinct; do not infer immediate getter filtering solely from a species' natural diet. Record every fixture's successful pre-capture getter before attributing a later mismatch to serialization.
