## Event behavior that affects the design

* `net.minecraft.world.entity.LivingEntity.drop(ItemStack, boolean, Prediction, boolean, boolean, Consumer)` creates the item entity, runs the optional consumer, dispatches `PlayerDropItemEvent` for a player, checks cancellation, and only then calls `Level.addFreshEntity`. `CraftEventFactory.doEntityAddEventCalling` dispatches `ItemSpawnEvent` for item entities. Thus the normal player-drop path allows recording the UUID as untrusted **before** its spawn callback. A spawn listener must not overwrite that decision. Cancellation returns the stack to the player and avoids addition. This is an inspected path, not a universal guarantee for plugins spawning items.
* `CraftEventFactory.callItemSpawnEvent` supplies the item entity; it supplies no producer block, source inventory, or production cause. The public spawn API likewise only identifies the spawned item/location. A newly spawned UUID inside the mechanism proves location and time, not that the farm produced it.
* `net.minecraft.world.level.block.entity.HopperBlockEntity.addItem(Container, ItemEntity)` dispatches `InventoryPickupItemEvent` **before** copying the item stack and inserting it. Cancellation returns immediately. Successful insertion can consume the whole entity or leave a partial remainder with the same UUID. Do not retire provenance merely because a pickup event fired; insertion may fail or be partial.
* `HopperBlockEntity.callPushMoveEvent` / `callPullMoveEvent` pass the actual source and destination inventories; `getInitiator()` is not a substitute for examining both. The API documents restoration on cancellation and special behavior when the event item is modified. Cancel rejected transfers without rewriting `getItem()`/`setItem()`. Source contents observed in the callback may already reflect temporary removal, so this callback is unsuitable for reconstructing an exact committed slot ledger. [API contract](https://jd.papermc.io/paper/26.1.2/org/bukkit/event/inventory/InventoryMoveItemEvent.html).
* `net.minecraft.world.entity.item.ItemEntity.merge(ItemEntity, ItemStack, ItemEntity, ItemStack)` calls `CraftEventFactory.callItemMergeEvent(donor, receiver)` before changing stacks. `getEntity()` is the donor and `getTarget()` the receiver. The receiver survives; the donor is discarded only if emptied. Partial merges retain both UUIDs. Cancel a merge when provenance differs, including unknown versus trusted and farm A versus farm B. Same-session trusted merges can proceed without copying UUIDs because both UUIDs were already trusted. See the local methods and the public merge contract linked above.
* `net.minecraft.core.dispenser.DefaultDispenseItemBehavior.spawnItem` dispatches `BlockDispenseEvent` before `addFreshEntity`. `ShearsDispenseItemBehavior.execute` also dispatches `BlockDispenseEvent`; `tryShearEntity` subsequently calls `BlockShearEntityEvent`, then `Shearable.shear`. A blanket dispense cancellation disables automatic wool production. A dispense event itself supplies no future item entity UUID, so a generic time/location guess is not a reliable provenance correlation.
* Paper hopper optimization can suppress move events: inspect `HopperBlockEntity.skipHopperEvents`, `skipPullModeEventFire`, `skipPushModeEventFire`, and `callPrepareTransferEvent`. The installed `server/config/paper-world-defaults.yml` has `hopper.disable-move-event: false`. Require the effective world setting to remain false during profiling; an event-only boundary has no protection when events are disabled. Avoid implementation-specific assumptions that every attempted slot produces an event.

## Recommended conservative design

Use three separate sets: mechanism blocks `M`, registered output container blocks `O`, and the expanded-by-two protected cuboid `P`. The expanded shell is an isolation boundary; it is not a production-origin allowance. Outputs must remain exterior and adjacent according to the agreed one-block rule, and every block of a multi-block output must satisfy the rule. Index sessions by world and protected chunks, but classify inventory endpoints independently of whether their initiator or chunk lies in `P`.

Before enabling measurement, enumerate all block inventories and inventory-bearing entities touching `P`. Reject nonempty internal transport/storage inventories; outputs retain their measured baseline. Reject existing item entities in `M` (or require removal before start), and treat all other existing/outside items as unknown. Perform validation and listener/session activation on the main thread without a tick gap. Keep the expanded shell's chunks available if the implementation scans it. Merely finding no players in `M` does not establish that inventory carriers or loose items are absent.

Classify complete logical inventories, not only `Inventory.getLocation()`: resolve both halves of `DoubleChestInventory` and treat a chest crossing classes as unsupported. The API explicitly exposes both side inventories. Resolve fixed block holders to their block set; use entity UUID plus current bounding box/location for entity holders. Null/unknown/virtual holders cannot be treated as safe internal sources. Prefer rejecting mobile inventory holders for this initial scope: a filled chest/hopper minecart or chest boat can cross the boundary without any inventory transfer event. Rechecking position when it later transfers catches some cases but misses the fact that its inventory already entered. If mobile transport must be supported, it needs explicit entry/movement isolation and initial provenance, rather than ordinary hopper handlers alone.

Apply this directed transfer policy:

| Source | Destination | Policy |
| --- | --- | --- |
| Validated fixed internal inventory in `M` | Another validated internal inventory | Allow |
| Validated fixed internal inventory in `M` | Registered output | Allow |
| Any outside, shell-only, unknown, other-session inventory | Internal inventory or output | Cancel |
| Registered output | Any inventory inside `M`, or another registered output | Cancel |
| Registered output | External sink outside `M` | Allow if output withdrawal is accounted for |
| Internal inventory | Outside/shell-only inventory | Cancel for the conservative closed session |

The output rule prevents initial baseline contents and already counted production from returning through a hopper chain. Boundary checks alone are insufficient: an output can feed an internal hopper and return to itself without crossing `P`. Likewise transfers between two registered outputs change per-output measurements. Keep outputs as sinks with respect to the mechanism. An external drain route may run through the protected shell, but every source outside `M` remains forbidden from feeding `M` or any output. Thus such a route can never return its contents, and no taint ledger is needed. All trusted production collectors must be inside the original mechanism cuboid.

If output draining is a hard requirement, classify the drain route as an external sink and allow output-to-external only, while continuing to cancel all ingress from that route. Internal inventory used for drainage cannot also serve as trusted production transport. Otherwise a separate per-stack/per-slot taint ledger must follow baseline/observed-output items through splits, merges, transformations, failed transfers, and every mutation path; the listed pre-transfer events alone do not provide a complete committed ledger. Also adapt production accounting: output snapshot differences cannot measure production accurately while arbitrary withdrawal occurs between snapshots.

For loose items, maintain per-session trusted UUIDs and a global/session untrusted-drop UUID set. Player drops anywhere are untrusted even if spawned inside `M`. At guarded inventory pickup, accept only an item trusted by that same session; cancel unknown, pre-session, outside-origin, or other-session items. Apply this to outputs too. Check destination ownership even when the item is just outside a chunk/cuboid edge: hopper suction can overlap the edge. Preserve UUID state through partial pickups, and cancel mixed-provenance merges anywhere either participating UUID is tracked, including just beyond `P`.

For the practical player/hopper-injection threat model, allow an item first spawned after session start inside `M`, provided it was not already marked untrusted. This preserves natural cactus/cane break drops, chicken eggs, and wool drops without enumerating each product type. **This is a constrained heuristic, not cryptographic provenance**: its safety depends on all other mutation/ingress guards below. A stricter supported-farm policy needs producer-specific adapters (block drop/growth, egg-producing resident chicken, dispenser shearing resident sheep), with tested causal attribution; the generic spawn event does not establish that relationship.

Automatic wool needs an explicit tooling exception: permit only predeclared shears in a fixed dispenser wholly inside `M`, and allow its shears action against a resident sheep wholly inside `M`; continue to prohibit replenishment/extraction, other dispenser/dropper releases, and manual shearing. Validate other dispenser slots empty. Shears durability and eventual breakage mean this is a tool-consuming farm, which must be reconciled with the glossary's no-input-farm definition as a product decision. Do not silently allow arbitrary filled dispensers. `BlockShearEntityEvent` offers a source block/entity pair for validation; it does not itself give spawned UUIDs.

## Necessary limits and verification

Implementation decision for #25: use the narrow **read-only pinned implementation adapter** to the
live hopper configuration, rather than the legacy disk snapshot described below. Initial equipment
material ambiguity **aborts the session with a reason**, rather than silently undercounting it.
Verified runtime scenarios are listed separately in [the acceptance guide](../testing/profiling-input.md);
the research checklist at the end is not a claim that every permutation has been executed.

### Initial equipment is finite input, and death drops bypass the obvious listener

Checking `InventoryHolder` contents does not check a mob's or armor stand's equipment. An initial zombie holding a stack of valuable items can die and release finite initial input as apparently new production. Capturing original actor UUIDs plus initial equipment materials is useful, but **`EntityDropItemEvent` alone cannot reliably attach that actor provenance to death-drop UUIDs on this build**.

Pinned evidence: `Entity.spawnAtLocation(ServerLevel, ItemStack, Vec3, Consumer)` checks whether a `LivingEntity` has a nonnull `deathDropItems` list. During death it queues `Entity$DefaultDrop` and returns without constructing an entity. Later `Entity.lambda$spawnAtLocation$0` directly constructs an `ItemEntity` and calls `Level.addFreshEntity`; that callback bypasses `EntityDropItemEvent`. Normal non-death `Entity.spawnAtLocation(ServerLevel, ItemEntity)` does emit `EntityDropItemEvent` before `addFreshEntity`, so a UUID blacklist works for that direct path only. `Mob.dropCustomDeathLoot` uses the deferred stack-drop path for equipment. `ArmorStand.brokenByAnything` likewise queues equipment as `DefaultDrop`; its callback `lambda$brokenByAnything$1` calls `Block.popResource`, bypassing the entity-drop event too. `EntityDeathEvent` supplies stacks, not the future spawned item UUIDs.

A simple conservative public-API policy is to collect initial equipment materials across the session and never trust spawned items with any of those materials for that session. An iron helmet then does not exclude iron ingots; a held diamond stack cannot become measured diamond production. This may undercount legitimate newly produced items of the same material, so report the restriction. More selective actor-specific attribution requires a tested causal adapter or temporary private markers on death-event drop stacks (which mutates the resulting world items and needs compatibility/cleanup work). Do not claim that the direct entity-drop event covers all equipment death drops. Include initial equipped zombie and equipped armor stand death in runtime acceptance.

### Checking the hopper configuration without reflection

On this exact build, public `Server.spigot().getPaperConfig()` calls `CraftServer$2.getPaperConfig`, which delegates to `PaperConfigurations.createLegacyObject`. That method **rereads configuration files**, rather than serializing effective live `WorldConfiguration` objects. It creates the root section `__________WORLDS__________`; its `__defaults__` child contains the defaults YAML, and a child named exactly `world.getName()` contains each loaded world's override YAML. Use direct child lookup rather than interpolating a potentially dotted world name into a path. Read `hopper.disable-move-event` from the world child when present, otherwise the defaults child, otherwise the native default `false` (confirmed in `WorldConfiguration$Hopper` constructor). Require Boolean values; reject ambiguous configuration rather than coercing it.

This public snapshot follows the actual configured global directory and Paper's actual world config paths, avoiding hardcoded guesses. On the installed 26.3 server the files are `server/config/paper-world-defaults.yml` and `server/world/dimensions/minecraft/{overworld,the_nether,the_end}/paper-world.yml`, with path `hopper.disable-move-event` in both levels. Do not assume `<world>/paper-world.yml` on this version. Both `World` and `World.Spigot` lack a public effective Paper-config getter in the inspected API.

Consequently this is a reliable **on-disk inherited setting check**, not proof of effective runtime state after an un-reloaded edit. Checking at plugin/session startup plus an operational requirement to reload/restart after edits and avoid configuration changes during profiling is the public-API option. An absolute live-state guarantee would need a pinned implementation adapter to `ServerLevel.paperConfig().hopper.disableMoveEvent` (outside public API), or a separate controlled runtime capability test; a file check must not be advertised as that guarantee.

This design protects against ordinary player insertion and hopper/item transport; it cannot defend against arbitrary plugins, commands, or administrators mutating inventories or spawning entities. Other plugins must not uncancel rejected events or write inventories directly. A spawn-inside heuristic also needs isolation against outside explosions, piston/container movement, fluid/block break effects, entity death drops, vehicles entering with inventory, and dispensers throwing items across the boundary. Initial empty inventories do not prevent an outside entity/container from being destroyed inside later. Existing guard coverage must be audited before claiming full isolation.

Fail/cancel the session when a supported invariant changes rather than silently accepting ambiguous provenance. Clean UUID/session/chunk indexes on cancellation, completion, unload/removal as appropriate, and restart; do not carry trust into a later profiling session. Avoid persistent item metadata or normalized item types as provenance: normalization intentionally discards individual properties, and equal materials can have different origins.

Required on-server checks on the pinned build: outside hopper push and pull; existing hopper-chain return; output baseline extraction/return entirely inside `P`; two-output crossfeed; player drop outside carried by water; drop inside/at border; full and partial trusted/unknown merges in both directions; failed/partial pickup; suction across chunk edge; straddling double chest; prefilled minecart/boat ingress; hopper event setting disabled; cactus, cane, egg and sheep/shears farms; initial filled internal inventory; valid startup/cancellation/restart cleanup. The event order and bytecode findings above do not replace these runtime tests.
