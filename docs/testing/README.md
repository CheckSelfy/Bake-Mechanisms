# Миры и сценарии проверки

Набор для [задачи #2](https://github.com/CheckSelfy/Bake-Mechanisms/issues/2). Источник требований — [спецификация MVP](../../.scratch/bake-mechanisms-mvp/spec.md) и [ADR-0001](../adr/0001-replace-farms-with-snapshots-and-fillers.md). Готовые миры создаёт отдельный инструмент `BakeTestFixtures`; он не включается в `bake-mechanisms.jar` и не нужен игровому серверу.

Для ручной проверки в Minecraft 26.3 используйте [небольшой общий мир из двух извлечённых ферм PPL9](manual-farm-lab.md): `python scripts/farm-lab.py run`, затем Multiplayer → `127.0.0.1:25566`. [NBT-структуры и манифест](../../test-worlds/ppl9/README.md) находятся в репозитории; из них создаются отдельные копии для ручного и headless-прогона. Полная исходная карта не требуется.

## Быстрый запуск

Для слайма-заполнителя #32: [галерея девяти размеров, палитра и проверка сохранения/защиты](slime-filler.md).

Для защиты профилирования #25: [подготовка фермы, ручные атаки и автоматические проверки](profiling-input.md).

После #25 перед ручным профилированием очистите внутренние инвентари, кроме воронок, включая бочку
`snapshot-marker`. Лежащая продукция запуску не мешает и не считается новой. Автоматический correctness-драйвер очищает инвентари
сам и возвращает маркер после замера перед стазисом, исключительно для проверки снимка.

Для отдельного аудита снимков сущностей #22: [матрица и запуск двухпроцессной проверки NBT](entity-nbt.md).

Нужны JDK 25 (`JAVA_HOME`), Python 3.11+ и сеть для первой загрузки Gradle/Paper. Minecraft-клиент для генерации и smoke-проверки не нужен. Команды одинаковы на Windows, Linux и macOS:

```text
python scripts/test-worlds.py prepare --accept-eula
python scripts/test-worlds.py smoke --farms 16
python scripts/test-worlds.py export
```

`--accept-eula` означает принятие [Minecraft EULA](https://aka.ms/MinecraftEULA) для локального сервера. Загружаются те же Paper 26.3 build 246 и Mojang JAR, что в `scripts/setup-test-server.sh`; SHA-256 проверяются. `prepare` выполняет `build` и `fixturesJar`. Сервер создаётся в игнорируемом `run/fixture-lab/`, доступен только по `127.0.0.1:25566`, работает с `online-mode=false`. Данные существующего `server/` не затрагиваются.

`smoke` создаёт три мира, проверяет структуру, наблюдает выходы 1200 серверных тиков, отдельно проверяет сбор искусственно выросшего кактуса, штатно останавливает сервер и проверяет сохранённые миры после повторного запуска. Наблюдения сохраняются в `plugins/BakeTestFixtures/observations/`, полный лог — в `fixture-console.log` и `logs/`. Пустой выход в естественном наблюдении — результат измерения, а не успешная проверка производства.

Архив `build/test-worlds.zip` содержит общий каталог `lobby/` с тремя тестовыми измерениями, их общими метаданными, манифестом и наблюдениями. Paper 26.3 хранит измерения в `lobby/dimensions/minecraft/<имя>/`; копирование только этих подкаталогов теряет общие данные уровня. Это соответствует [структуре Paper 26.x](https://papermc.io/news/26-1/). Серверные JAR и EULA в архив не включаются. Экспорт откажет, если сервер удерживает блокировку уровня. Для переноса подготовьте **новый** сервер через `prepare --server run/imported --accept-eula`, распакуйте архив в этот каталог и выполните `python scripts/test-worlds.py verify --server run/imported`. Уровень должен называться `lobby` (`level-name=lobby`). Генератор загрузит измерения по манифесту и проверит UUID. Для загрузки без инструмента нужна отдельная настройка загрузки дополнительных миров.

## Воспроизводимость и сброс

Seed `20261110`, каменная плоскость на Y=63, полдень, без смены погоды/времени и естественного появления мобов, `randomTickSpeed=3`. Строительство не копирует чужие карты и не требует WorldEdit. Содержимое мира после запуска закономерно меняется: seed и конструкция воспроизводимы, UUID миров/сущностей и случайные урожаи — нет.

Генератор отказывается перезаписывать миры. Для чистого повтора используйте новый каталог:

```text
python scripts/test-worlds.py prepare --server run/fixture-repeat --accept-eula
python scripts/test-worlds.py smoke --server run/fixture-repeat --farms 16
python scripts/test-worlds.py export --server run/fixture-repeat --output build/test-worlds-repeat.zip
```

Для сброса отдельного сценария штатно остановите сервер и восстановите **весь** сохранённый набор: миры, `plugins/BakeMechanisms/` и `plugins/BakeTestFixtures/`. Нельзя возвращать только мир, оставляя более новые снимки/регистрации плагина. Исходный экспорт smoke не содержит регистрации ферм и подходит для первоначальной подготовки; это не резервная копия состояния полного MVP. Не запускайте две копии с одинаковым портом одновременно.

## Состав миров

| Мир / ID | Назначение | Исходный механизм | Выход |
|---|---|---|---|
| `bake_blocks` / `blocks` | Блочная ферма | 49 кактусов, песок, железные прутья, 225 направленных воронок | Бочка `(16,64,7)` |
| `bake_entities` / `entities` | Ферма с сущностями | 8 взрослых именованных кур, стеклянный загон, 28 воронок | Бочка `(16,64,7)` |
| `bake_performance` / `perf001`… | Масштабируемый нагрузочный мир | Копии блочной фермы, 16 по умолчанию, до 100 | Отдельная бочка каждой фермы |

Механизм каждой фермы: включительный кубоид `(X,63,Z)` — `(X+15,70,Z+15)`, объём 2048 блоков, один чанк. Выход `(X+16,64,Z+7)` находится в соседнем чанке. Для `blocks` и `entities`: `X=Z=0`. Для `perfNNN`, где `i=NNN−1`, `C=ceil(sqrt(N))`, а `N` — число performance-ферм: `X=48*(i mod C)`, `Z=48*floor(i/C)`. По умолчанию 16 ферм образуют компактную сетку 4×4 с центром `(80,65,80)`, удобную для одного наблюдателя. Между механизмами нет общих чанков, выходы не входят в чужие механизмы. Манифест с UUID миров — `plugins/BakeTestFixtures/manifest.yml`. В обоих correctness-мирах внутри механизма есть отдельная, не подключённая к производству бочка `(0,65,0)`: слот 0 содержит 3 камня с именем `snapshot-marker`. Она позволяет проверить сохранность внутреннего инвентаря без перемещения маркеров в выход. В performance-копиях этой бочки нет.

Кактусы находятся на Y=66, X=`X+2, X+4, …, X+14`, Z=`Z+2, Z+4, …, Z+14` (49 растений). Рост рядом с прутьями на Y=67 ломает выросший блок; часть выпавших предметов может уничтожаться кактусом. Измеряется фактический собранный выход, а не теоретический урожай. Входные ресурсы и действия игрока для сбора не расходуются. Выпавшие предметы — временные сущности даже в «блочном» сценарии: перед снимком дождитесь их сбора; если они остаются, требуется поддержка сериализатора `Item` либо явный отказ.

Куры не требуют корма для кладки. Их начальные таймеры заданы как `200+40*i` тиков, `i=0..7`, чтобы проверить сбор при подготовке; следующие таймеры задаёт игра. Это известное начальное состояние, **не** равномерный генератор яиц. Перед профилированием/бенчмарком выдержите 12000 тиков прогрева, опустошите выход и убедитесь, что следующая продукция получена без `probe` или вмешательства в таймеры. Поддержка снимков `Chicken`, UUID, имён, PDC, возраста и таймера кладки проверяется на настоящем Paper через `stasisSmoke`; результаты полного цикла — в [журнале #11](results.md). Несколько типов сущностей и транспорт/пассажиры также покрывает `stasisSmoke`.

## Команды инструмента

Команды доступны консоли и OP (`bakefixtures.manage`); обычному игроку для `/bake` OP не нужен. В консоли начальный `/` опускается.

| Команда | Результат |
|---|---|
| `bakefixtures create correctness` | Создать два correctness-мира, отказать при существующем мире |
| `bakefixtures create performance 16` | Создать отдельный performance-мир с указанным числом ферм, 1–100 |
| `bakefixtures list` | Координаты всех кубоидов и выходов |
| `bakefixtures check` | Проверить исходную структуру; применять до стазиса или после восстановления |
| `bakefixtures visit blocks` | Телепортировать игрока на безопасную площадку рядом с фермой |
| `bakefixtures hold` | Удерживать чанки механизмов и выходов инструментом |
| `bakefixtures release` | Снять **только** тикеты инструмента |
| `bakefixtures observe blocks 3600` | Сохранить содержимое выхода до/после известного числа тиков |
| `bakefixtures observe all 1200` | То же для всех ферм |
| `bakefixtures probe blocks` | Искусственно вырастить верхние блоки четырёх кактусов для проверки сборщика |

`probe` нужен только для диагностики конструкции: предметы настоящие, но причина роста искусственная. Не используйте его во время профилирования, стазиса и замеров. `observe` ничего не добавляет и не забирает, не включает принудительную загрузку и не вычисляет профиль. Сравнивайте `before/after` и зафиксированные тики, учитывая постороннее добавление/изъятие.

После генерации чанки удерживаются инструментом. После рестарта — нет; используйте `hold`, если нужно продолжить подготовку. Перед проверкой тикетов Bake Mechanisms и сравнением стазиса обязательно выполните `release`, иначе инструмент скроет утечки тикетов и стоимость исходных чанков. Естественный рост кактусов зависит от наличия игрока в зоне случайных тиков; принудительная загрузка сама по себе не доказывает работу случайных тиков. Для production-preview нужен клиент рядом с фермою. В performance-мире фиксируйте расположение игроков и выбирайте рабочий набор, реально охваченный случайными тиками; нельзя сравнивать активный оригинал с неработающей дальней фермой.

## Приёмка

1. [Сценарии correctness](scenarios.md) — начальные условия, шаги и ожидаемые результаты.

Его границы и фактические результаты записываются в [журнал](results.md); непроверенные игровые действия не считаются `PASS`. Полный correctness-review — #11, реальный performance-review — #12.
