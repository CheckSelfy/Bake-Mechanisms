# PPL9 high-load mob-farm world

This disposable world is the high-load input for the performance review in issue #12. It is built from **three independent no-input zombified-piglin gold farms** using the collection mechanism extracted from the user-provided `E:/Sites/ppl9-farm` save. The source world has no matching gold farm: its dense piglin mechanisms are gold-consuming barters, so the builder deliberately reuses only an extracted PPL9 collection frame and changes the disposable spawner type.

Each plot has a native spawner, zombified-piglin AI/aggro, iron-golem combat, drops and hopper transport. The iron golem and the spawned `ZOMBIFIED_PIGLIN` are both audited entity types, and gold nuggets are generated by native death loot rather than injected by the lab. The deliberately high-load configuration is 128 spawn attempts every 5–10 ticks, with up to 1024 nearby mobs; this is four times the preceding high-load schedule. This gives a no-input production profile that can legitimately move from original operation to stasis.

The lab builder creates `farm_lab_mob_performance` on first start and places three plots in a compact 2-by-2 layout. Each inclusive mechanism is `(x,64,z)` through `(x+12,88,z+12)` and has an external double chest at `(x-1,71,z+5..6)`; spacing is 17 blocks, so every mechanism occupies distinct chunks, mechanisms and outputs never overlap, and the farms' profiling protection belts (each mechanism expanded by 2 blocks) do not overlap either: all three farms can be profiled at the same time. With the earlier 16-block spacing neighbouring belts shared one column and `ProfilingService` refused to profile a second farm while the first was profiling. Plot names are `mobperf01` through `mobperf03`. The shared glass AFK/profile pad is at `(16,89,16)`, in the gap between the belts: standing there never enters a protected area, and it is 13–15 blocks from every spawner, so one player there activates all three. The lab checks both conditions on start. Labs generated before the spacing change (`mob-performance-v7.txt`) are refused; run `gradlew resetFarmLab` to regenerate them.

Use `python scripts/farm-lab.py run`, then `/farmlab visit mobperf01`, `/farmlab corner mobperf01 1|2|output`, and the normal `/bake` workflow to register/profile/stasize the plots. `/farmlab list` prints all coordinates, including the explicit safe AFK/profile position. The builder deliberately does not bulk-register or profile farms, so the performance review still uses the production command contract. `/farmlab visit` sends the player to the shared AFK pad; use that exact position in both benchmark phases.

After the three farms are in the intended phase, run `/farmlab benchmark <label> <ticks>` while standing on that pad. The window is counted in game ticks of the benchmark world, so a `/tick freeze` cannot stretch it; scheduler ticks are recorded beside them (`server-ticks-without-game-tick` is non-zero only if the game was frozen). The command writes `plugins/BakeFarmLab/benchmarks/*.yml` with start/end game time, wall time, TPS, the MSPT distribution of every tick in the window (mean, median, p95, max), the players and their positions, the farms' states, initial and final resolved-double-chest inventories and their delta, persisted profile rates, the AFK position, and the Spark artifacts. When the server has the bundled Spark, the command runs `spark profiler start` and `spark profiler stop --save-to-file` itself, so the profile is saved under `plugins/spark` and never uploaded; `spark-artifacts-created` lists the new files.

This world is a benchmark input, not a long-running automated test. Structural checks and compilation are sufficient when changing it; run the measurement protocol in [performance.md](../../docs/testing/performance.md) when an operator is ready to collect MSPT and production data.
